What it looks for

Eight patterns behind most Supabase leaks.

Each finding links to a page that explains it in plain English, shows the fix and says when the pattern is intended. Only tables in the public schema are analysed.

IDWhat we flagSeverity
PL-001A read policy open to anonymous visitors, not limited to the signed-in user, on a table with email, phone, address, date-of-birth or ID-number columns.critical
PL-002Any signed-in user can read every row, so signing up unlocks other people’s data.high medium
PL-003Row level security is on but the table has no policies, so nobody can use it through the API (the app may be broken).low
PL-004An UPDATE policy without WITH CHECK.medium
PL-005A policy that is always true, such as USING (true).high to low
PL-006A SECURITY DEFINER function with no fixed search_path, or callable by anonymous visitors.high medium
PL-007A storage bucket created or updated with public = true.medium
PL-008A table where row level security is never enabled: anyone with the public key can read and change every row.critical high

For engineers

Run it from your terminal, CI or agent.

The same check is a public endpoint. It returns JSON with every table, finding, file and line, so you can fail a build on a critical finding. It’s also a tool in our MCP server, so your coding agent can call it.

  • Reads supabase/migrations/*.sql on the default branch, pinned to its latest commit, in filename order
  • At most 60 files and 2 MB; the result says when it stopped early
  • Results are cached for 10 minutes per repo and commit
  • 20 requests per network per hour, failed lookups included

Questions

About the free check

Something else? Email the founder.

My result is clean. Am I safe?

Not necessarily. No findings means none of the eight patterns appear in your migration files. Access can still leak through grants, views, functions or settings made outside the repo. The full check rebuilds the database and tests what each identity can actually read, which is the only way to know.

Do you keep my repo or code?

We keep the repo name and a hashed network address to enforce the hourly limit, and we cache the result for 10 minutes so repeat checks are instant. We don’t clone the repo; we fetch the migration files from GitHub and analyse them in memory.

Can it check a private repo?

Not yet. Private repos need our GitHub App, which is coming. Until then, both this tool and the full check work on public repos only.

My migrations aren’t in supabase/migrations.

The tool only reads supabase/migrations at the root of the default branch, which is where Lovable, Bolt and the Supabase CLI put them. If yours live elsewhere, tell us and we’ll look at supporting your layout.

Is a finding always a leak?

No. A product catalogue or a public blog is meant to be readable by anyone, and the tool can’t know your intent. That’s why each finding page explains when the pattern is fine, and why the full check asks you plain-English questions before calling something a leak.
