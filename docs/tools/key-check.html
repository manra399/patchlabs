Supabase keys

Two keys look the same. One of them opens everything.

Supabase gives every project two keys that both start with eyJ. They are JSON Web Tokens, and the middle part says which role the key carries. Builders paste the wrong one into a VITE_ variable more often than you’d think, because the variable names and the dashboard boxes sit side by side.

Newer projects use sb_publishable_… and sb_secret_… keys instead. The same rule applies: publishable is fine in the browser, secret never is.

KeyIn browser codeWhy
role: anon
sb_publishable_…		fineMeant to be public. Your row level security rules decide what it can read, so those rules are what matter.
role: service_role
sb_secret_…		neverSkips row level security. Anyone who finds it can read, change and delete every row in every table. PL-010

Questions

About the key check

Something else? Email the founder.

Is it really safe to paste a key here?

The check is a script on this page. It reads the text box and draws the result; it makes no network request and stores nothing. You can confirm it: open your browser’s developer tools, go to the Network tab, and run a check. If you’d rather not paste a live key anywhere, revoke it first and paste the old one: the check reads the key’s format, not whether it still works.

It found a key. What now?

Revoke it at the provider first (each finding links to the page), then create a new one and keep it on the server: an edge function, a backend route or your host’s secret settings. Deleting the line is not enough if the key was ever committed or deployed, because it stays in your git history and in old builds. PL-011 explains the history part.

How do I check my live site?

Open your site, press View Source or open the Sources tab in developer tools, and copy the main JavaScript file (usually /assets/index-….js). Paste it here. That file is exactly what every visitor downloads.

No keys found. Am I safe?

For the text you pasted, the known secret formats aren’t there. Keys can still sit in other files, in old commits, or in a format we don’t recognise. And a public anon key is only as safe as your row level security rules, which the free RLS check reads and the full check proves.
