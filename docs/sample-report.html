03 The leak · finding 1 of 1

criticalPL-001readable by anyone

Anyone with the app’s public key can read every profile, including email and phone.

  • table public.profiles
  • policy “Profiles are viewable by everyone”
  • 20260101000000_init.sql:12

The rule that leaks

supabase/migrations/20260101000000_init.sql
 3 CREATE TABLE public.profiles (
 4   id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
 5   user_id uuid REFERENCES auth.users (id) ON DELETE CASCADE,
 6   full_name text,
 7   email text,
 8   phone text,
 9   created_at timestamptz DEFAULT now()
10 );
11 ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;
12 CREATE POLICY "Profiles are viewable by everyone" ON public.profiles FOR SELECT USING (true);
13 CREATE POLICY "Users can update own profile" ON public.profiles FOR UPDATE USING (auth.uid() = user_id);

The exploit

Any one of these returns every user’s row. Nothing here needs a password: the project URL and public key are in the app’s JavaScript.

From a browser (HTTP)

terminal
# URL and key come from the app's own JavaScript bundle
curl "https://<project>.supabase.co/rest/v1/profiles?select=full_name,email,phone" \
  -H "apikey: <public anon key>"

supabase-js

browser console
const { data } = await supabase
  .from('profiles')
  .select('full_name, email, phone')
// returns every user's profile, not just yours

SQL, as the lab runs it

lab Postgres
-- anonymous visitor = the anon role
set local role anon;
select * from public.profiles;
-- 2 rows: both seeded test users

What came back

Why it matters

  1. The public key isn’t a secret. src/supabase.ts builds the client from VITE_SUPABASE_ANON_KEY, and the build puts it in the JavaScript every visitor downloads. That’s normal for Supabase. It means the access rules are the only lock.
  2. This rule leaves the lock open. USING (true) with no TO clause applies to every role, including anon. One request lists every user’s name, email and phone number.
  3. That can be a reportable breach. In the UK, certain personal data breaches must be reported to the ICO within 72 hours. Work out what a leak would cost you.
  4. Closing it won’t break the app. The app’s own code only ever reads the signed-in user’s profile, so owner-only access is what it already expects. That’s why this report has no questions for you.
src/Account.tsx (from the repo)
// The signed-in user's own account page.
const { data } = await supabase.from('profiles')
  .select('full_name, email, phone').eq('user_id', userId).single()

04 The fix

One new migration, two statements.

Written by the smallest Claude model on its first attempt. It replaces the open read rule with one that lets each user read only their own profile. Your existing migration stays as it is.

What changes

policy on public.profiles
CREATE POLICY "Profiles are viewable by everyone" ON public.profiles FOR SELECT USING (true);
CREATE POLICY "Users can view own profile" ON public.profiles FOR SELECT USING (auth.uid() = user_id);

The migration file

supabase/migrations/20261109165700_patchlabs_leak_fix.sql
-- Fix: Replace overly permissive "everyone can read" policy with owner-only access
-- The original policy "Profiles are viewable by everyone" allowed anonymous and any signed-in user
-- to read all columns (email, phone) from all profile rows.
-- Change: Only allow users to read their own profile (where user_id = auth.uid())

DROP POLICY "Profiles are viewable by everyone" ON public.profiles;
CREATE POLICY "Users can view own profile" ON public.profiles FOR SELECT USING (auth.uid() = user_id);
Download the fix (.sql) Demo: only the repo owner can commit

On your report, “Commit the fix on GitHub” opens GitHub’s new-file page with the migration filled in: review it and press “Commit changes”. Automatic pull requests need our GitHub App, which is coming.

Risk that something behaves differently: low

From the report: only anonymous and other-user access is removed, which the frontend never relied on. Users still read their own profiles as before.

How to apply it

  1. Add the file to supabase/migrations/, keeping the timestamped name so it runs last.
  2. Review and merge it like any other change.
  3. Deploy as usual. In Lovable or Supabase it applies on the next database push.

07 Key scan

No exposed keys, in the code or its history.

We searched every file in the repo and every commit in its git history for AI, payment and database keys. A key deleted from the code is still in the history, so we read both.

0

0 keys found

The app reads its Supabase URL and public key from environment variables (src/supabase.ts), so nothing is committed. The public key is meant to ship to browsers; that’s why the access rules in section 03 matter.

If a key is found, the report tells you to

  1. Rotate it with the provider first. Deleting it from the code doesn’t help: it stays in the git history.
  2. Check the provider’s usage logs for calls you didn’t make.
  3. Move it to an environment variable or server-side secret. Keys for AI or payment services should never reach the browser.
  4. Rewrite the history only after rotating, if you want it gone from old commits too.

09 Receipt

A signed record anyone can check.

Every finished check gets a receipt signed with Ed25519. It fixes the result, the hash of the fix file and every decision, so anyone can confirm none of them changed after we issued it.

This demo isn’t signed. The sample is served as a static file with the id “sample”, so there’s no signature to verify. A real check’s receipt has these same fields with its own id, plus signature, key_id and algorithm.

Verify a real receipt

  1. Fetch GET https://api.patchlabs.dev/receipts/<check id>. It’s public by link, like the report.
  2. Fetch our public key from /.well-known/patchlabs-receipt-key on the API and check the key_id matches.
  3. Serialise receipt as JSON with sorted keys and no spaces, and verify the signature against it.
verify_receipt.py
import base64, json, urllib.request
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PublicKey
API, CHECK = "https://api.patchlabs.dev", "<check id>"
r = json.load(urllib.request.urlopen(f"{API}/receipts/{CHECK}"))
k = json.load(urllib.request.urlopen(f"{API}/.well-known/patchlabs-receipt-key"))
assert r["key_id"] == k["key_id"], "signed with a different key"
msg = json.dumps(r["receipt"], sort_keys=True, separators=(",", ":")).encode()
pub = Ed25519PublicKey.from_public_bytes(base64.b64decode(k["public_key"]))
pub.verify(base64.b64decode(r["signature"]), msg)  # raises if anything changed
print("receipt is genuine:", r["receipt"]["status"], r["receipt"]["tables_leaking"])
