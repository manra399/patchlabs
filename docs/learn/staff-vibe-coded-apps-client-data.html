Launch and other stacks

Your staff are vibe-coding apps with client data. Find them and check them in an afternoon.

On 18 November a legal-tech vendor asked Hacker News a question many firms now have. Lawyers and paralegals at its client firms are building their own apps with Codex and Cowork. One built a dashboard of aggregated client data and put it on a public Vercel URL. Nobody outside the firm opened it and it came down quickly, but nobody had known it existed. This guide is for the person who now has to find these apps and decide which ones are safe.

By Manraj Singh Dhillon, technical founderChecked 18 Nov 2026, AI builders added 19 Nov7 min read

TL;DR

  • On Vercel, the recommended setting (“Standard Protection”) locks preview links but leaves the production domain public. The URL people actually share is the one that is open.
  • Fix: set the team default to All Deployments with Vercel Authentication. It is on every plan with no add-on, and it covers projects created after you change it.
  • Locking the URL does not lock the data. If the page reads Supabase from the browser, the database answers anyone who has the key, and the key is in the page’s JavaScript. Check the database rules too.
  • Our free script lists every project in a Vercel team, its protection level, and what a signed-out stranger gets: vercel_public_apps.py.
  • Apps built inside Grok, ChatGPT, Lovable or Base44 never touch your Vercel team. A study of 37,571 Grok apps found 94.7% opened without sign-in. Find your staff’s apps in your own DNS logs with builder_apps_from_logs.py.
  • Then run three tests on each app that holds client data: signed out, straight to the database, and as a second user.

This is for IT leads, operations staff and the vendors who serve them, at law firms, clinics, accountants and agencies, anywhere non-engineers now ship internal tools. You need admin access to your Vercel team. You don’t need to read code.

Why the dashboard was public

Vercel lets you choose who can open a project’s URLs. There are two parts: a method (how visitors prove who they are) and a scope (which URLs are covered). Vercel’s documentation calls Standard Protection “the recommended option for most projects”, and it protects all domains except production domains. Preview links that change on every deploy are locked. The stable address you get when you press Deploy, and any custom domain, stay open to anyone.

So someone can do everything the platform suggests and still publish client data. Builders that deploy for you (v0, Codex, Cowork and the rest) use the same project settings. Deployments that are not locked and have no custom domain are also, in Vercel’s words, public and can be indexed by search engines.

Scope (what the API calls it)Production URLPlans
None (null)PublicAll
Standard Protection (all_except_custom_domains)PublicAll
Legacy standard (prod_deployment_urls_and_all_previews) or previews only (preview)PublicAll
All Deployments (all)Login requiredAll, no add-on with Vercel Authentication

From Vercel’s Deployment Protection docs and its public API description, read 18 Nov 2026. Password Protection costs $20 a month per project on Pro and isn’t on Hobby. Passport (your own identity provider) and Trusted IPs are Enterprise only.

Lock every new project by default

  1. In Vercel, open your team settings, then Deployment Protection, and set the default for new projects to All Deployments with Vercel Authentication. Vercel applies this default to projects created after you set it. It does not change existing ones.
  2. Vercel Authentication lets in team members, project members with a viewer role, access groups, and signed-in Vercel users you have granted access. Anyone holding a shareable link or a bypass secret also gets in, so list those under each project’s Deployment Protection settings and revoke the ones nobody needs.
  3. Fix existing projects one at a time (the script below lists them). Switching scope also locks the project’s generated *.vercel.app production URL, so update any code that fetches its own VERCEL_URL.

This only covers projects in your firm’s team. Someone who signed up with a personal account on the free plan is outside it, and you won’t see their project. That is the next step.

Find the apps that already exist

In your Vercel team. Create a read-only token (Account Settings, then Tokens, scoped to the team) and run our script. It uses only the Python standard library and changes nothing. It sends nothing anywhere except the Vercel API and your own production URLs.

find public apps
curl -sO https://raw.githubusercontent.com/manra399/patchlabs/main/tools/tests-guides/vercel_public_apps.py
VERCEL_TOKEN=... VERCEL_TEAM=your-team-slug python3 vercel_public_apps.py
example output
client-dashboard
  scope: Standard: production domain PUBLIC
  client-dashboard.vercel.app: 200: PUBLIC, the page loads for anyone; its JavaScript reads Supabase directly (check RLS)

intake-form
  scope: All Deployments: production protected
  intake.yourfirm.com: 401: login required (good)

We tested the script against a mock of Vercel’s documented API response and against live public sites on 18 Nov 2026. We don’t have your team, so tell us if Vercel answers differently for you.

Outside your team. These turn up apps your admin panel never shows:

  • Your own domain. Every HTTPS certificate is logged publicly, so search crt.sh for %.yourfirm.com and look for subdomains nobody recognises. Apps on a bare *.vercel.app name won’t show up here.
  • Sign-ups with work email. Ask Vercel, Supabase, Lovable, Netlify and Replit which accounts use your company email domain. Many will tell an admin, or offer a domain claim on a team plan.
  • Ask, without blame. A two-line message (“if you have built a tool that touches client data, tell me and I’ll help you keep it”) finds more than any scan. The people building these tools are usually solving a real problem.

Apps built inside Grok, ChatGPT and other AI builders

Chat-based builders host the app themselves, so it never appears in your Vercel team, your certificate logs or your asset list. Each app gets its own address, such as four-random-words.grok.me. That name feels secret. It isn’t: every visit causes a DNS lookup, and passive DNS services record those lookups in databases anyone can search for a fee.

On 10 Nov 2026 the security firm Claroc published a test of 37,571 live apps made with Grok’s app builder. 35,578 of them (94.7%) opened for anyone without sign-in. About one in ten open apps held internal business or personal data, including a hospital staff roster of more than 3,500 people and a timesheet app whose script held 18 plaintext passwords. Grok’s publish panel offered “Anyone with the link”, “Invited users” and “Only you”, with “Anyone with the link” preselected. Switching to “Only you” gave strangers a 401 within seconds: the control worked, it just wasn’t the default. The Cloud Security Alliance wrote the study up on 11 Nov and notes it has not verified the figures independently.

BuilderApp addressDefault when you publish
Grok app builder*.grok.me“Anyone with the link” preselected (staff accounts “Only you”)
ChatGPT app builder*.<username>.chatgpt.site“Only me”
Lovable, Base44, Replit, Bolt*.lovable.app, *.base44.app, *.replit.app, *.bolt.hostPage public by default once published (some paid plans can limit it to your workspace); the data is only as closed as the database rules

Grok and ChatGPT defaults as reported by Claroc and the Cloud Security Alliance research note “Public by Default” (11 Nov 2026), read 19 Nov 2026. Check the setting in each builder before you rely on it; vendors change defaults after studies like this.

A sign-in screen is not proof. In one of Claroc’s own test apps, Grok added “Continue with Google” and then put every signed-in user on the team before checking membership, so any Google account could read, edit and delete every record. This is the same mistake as an RLS policy that only asks “is someone signed in” (PL-002). Sign in with an outside account that was never invited, and check you see nothing.

Find them in your own logs. Export a week of DNS resolver, firewall or web gateway logs, or any text file that lists hostnames, and run our script. It pulls out every hostname on a known builder domain, loads each page once signed out, and reports what a stranger gets. It prints secret types and email domains it finds in the page’s code, never the values. Add --org-domain to flag the open apps whose page mentions your email domain.

find builder apps in your logs
curl -sO https://raw.githubusercontent.com/manra399/patchlabs/main/tools/tests-guides/builder_apps_from_logs.py
python3 builder_apps_from_logs.py --org-domain yourfirm.com dns-export.csv
# --list-only makes no requests at all: it just lists the builder apps your staff opened
example output
quiet-amber-river-lamp.grok.me  (Grok app builder, seen 41x)
  200: OPEN, the page loads for anyone
  email domains in the page: yourfirm.com (212)
  SECRETS in the page's code: password in code. Treat as compromised and rotate.
  mentions yourfirm.com: likely yours. Switch it to invited users or Only you, or unpublish, then re-run.

private-tool.jdoe.chatgpt.site  (ChatGPT app builder, seen 3x)
  401: closed to strangers (good)

We tested the script on 19 Nov 2026 against a local mock of open, closed and redirecting apps, and against live grok.me and vercel.app addresses. Your logs also list public apps staff only visited, so confirm who owns an app before acting, and test only apps you can tie to your organisation.

For each open app that holds work data: ask the owner to switch it to invited users or “Only you”, or unpublish it, then confirm a private window gets an error page. If you can’t find the owner, report it to the builder for takedown. Rotate any password or key the script found in the page: it was readable by anyone while the app was open. Then add the builder to the staff rule below.

Three tests for each app

1. The signed-out test. Open the URL in a private window on your phone’s mobile data, not the office network. You should get a login page or a 401. The script does this for every production domain. If client data appears, take the deployment down first and ask questions after.

2. The database test. Many AI-built apps read their data straight from Supabase in the browser. Locking the page doesn’t change who the database will answer. The project URL and the public key ship inside the page’s JavaScript, so anyone who has ever loaded it still has them: a former employee, someone sent the link, anyone who saw it while it was public. When the script reports “reads Supabase directly”, test the tables themselves:

database test (with the app’s own public key)
# URL and KEY are in the page source; TABLE is a table the app shows
curl -s "$URL/rest/v1/$TABLE?select=*&limit=1" -H "apikey: $KEY" -H "Authorization: Bearer $KEY"
# []  or a permission error = good.  A row of client data = the database is open to anyone.

Our free RLS check reads the app’s migrations, if they are in a public repo, and lists every table a visitor can read. If the repo is private, our guide RLS on every table has one SQL query you can paste into the Supabase SQL editor instead.

3. The second-user test. If more than one person signs in, sign in as two test users and check that one can’t see the other’s matters, clients or files. Open a record, change its id in the address bar or the request, and see what comes back. A rule that only checks “is someone signed in” passes tests 1 and 2 and still shows every row to every user (PL-002).

A one-page rule for staff

  • Build anything you like. Deploy only to the firm’s team, where the default is All Deployments. In a chat builder such as Grok or ChatGPT, publish to “Invited users” or “Only you”, never “Anyone with the link”.
  • Every app has a named owner and is written down in one shared list: name, URL, what data it touches.
  • Client or personal data goes in only after the three tests above pass. Re-run them after big changes.
  • No personal accounts for work data. If you’ve already got one, move it, and we’ll help.
  • When the owner leaves, the app is handed over or switched off that week.

A prompt staff can give their builder

prompt
This app will hold client data. Before I deploy it:
1. List every table and storage bucket and say who can read and write each one
   when signed out, signed in as any user, and signed in as the owner.
2. Turn on row level security for every table, with policies so each signed-in
   user sees only their own (or their team's) rows. No policy may use true.
3. Make sure no secret key (service_role, sb_secret_) is in browser code.
4. Tell me the Vercel project setting I need so the production URL requires a
   login (Deployment Protection: All Deployments).
List every file you changed.

How PatchLabs checks for this

The script above handles the hosting side. For the data side, PatchLabs rebuilds an app’s database from its migrations in a lab, then reads it as a signed-out visitor, a signed-in stranger and the owner. It reports every table that answers the wrong person, with the rows it got back as proof. It writes the fix as a migration and re-runs the same reads to show the fix works. Your engineer, or the person who built the app, approves it. We never connect to your live database.
