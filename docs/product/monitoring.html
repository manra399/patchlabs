Monitoring

The next prompt can reopen the leak. Re-checks catch it.

AI builders change your database every time you ask for a feature. PatchLabs re-checks each app on a schedule, compares the result with the last run, and tells your team only when something new can be read.

Schedule

Re-checks run on their own. Run one any time.

Every verified app gets a schedule. Due checks are queued automatically, and “Run now” queues one immediately, for example right after you merge a fix.

Alerts

An alert means something new. Not the same leak again.

Each finished check is compared with the previous one, table by table. Your team hears about new leaks loudly and everything else quietly.

new
Readable now, not readable last time. The email subject says “New leak found”.
fixed
Readable last time, closed now.
still
Still readable. Listed, without a new-leak alert.
intended
Your team marked these tables as meant to be readable. Never alerted on.

Dismissals stick. Marking a table as intended is remembered for the app until someone approves the fix for it again. The decision, and who made it, goes into the signed receipt.

Webhooks

Straight into Slack, or anything that takes a POST.

Paste one https URL in workspace settings. Every finished check sends a JSON event with a text line, so a Slack incoming webhook works with no code at all.

  • A “Send test event” button in settings shows the status code you got back
  • Private and loopback addresses are refused
  • A broken webhook never loses the check: the email still goes out
POST your-webhook-url · check.finished
{
  "event": "check.finished",
  "text": "PatchLabs: you/your-app (Client A): leaks found and a tested fix is ready. https://patchlabs.dev/check?id=…",
  "check": {
    "id": "…",
    "app_id": "…",
    "repo": "you/your-app",
    "status": "done",
    "tables_leaking": ["bookings"],
    "new_leaks": ["bookings"],
    "fixed": ["profiles"],
    "suppressed": ["listings"],
    "url": "https://patchlabs.dev/check?id=…"
  }
}

CI

Re-check every time a migration lands on main.

Create an API key in workspace settings and add this workflow. It queues a check when a migration is merged, waits for the result and fails the build if anything is leaking.

Checks read your default branch, so this runs after the merge, not on the pull request. Re-proving every pull request before merge needs our GitHub App, which is coming.

API keys, webhooks and CI work on every plan, including Free. Each CI run counts as one of your monthly runs. API reference.

.github/workflows/patchlabs.yml
name: PatchLabs re-check
on:
  push:
    branches: [main]
    paths: ['supabase/migrations/**']
jobs:
  recheck:
    runs-on: ubuntu-latest
    steps:
      - name: Queue a check and wait for it
        env:
          PL_KEY: ${{ secrets.PATCHLABS_API_KEY }}
          PL_APP: ${{ vars.PATCHLABS_APP_ID }}
          API: https://api.patchlabs.dev
        run: |
          # a few seconds so GitHub serves the new commit
          sleep 15
          cid=$(curl -sf -X POST -H "X-API-Key: $PL_KEY" \
            "$API/v1/apps/$PL_APP/checks" | jq -r .check_id)
          for i in $(seq 1 60); do
            sleep 30
            r=$(curl -sf -H "X-API-Key: $PL_KEY" "$API/v1/checks/$cid")
            [ "$(echo "$r" | jq -r .finished)" = "true" ] && break
          done
          echo "$r" | jq '{status, tables_leaking, url}'
          [ "$(echo "$r" | jq -r .leaks_found)" = "false" ]

Questions

Monitoring FAQ.

How do I start monitoring an app?

Sign in with your email (no password), add the repo, and commit the patchlabs-verify.txt file the dashboard gives you. Once verified, the first check runs and the schedule starts.

What happens if a check is already running?

A second one isn’t queued; you’ll see a message saying one is in progress. Scheduled checks wait for the open one to finish.

Who gets the alerts?

Every member of the workspace, by email, plus the workspace webhook if you set one.

Can I turn re-checks off?

Yes. Set the app’s schedule to off and run checks only when you choose.
