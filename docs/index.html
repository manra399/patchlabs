The problem

The app works. That is exactly why nobody checks who else can read it.

01Exposed

AI builders ship databases strangers can read.

Your app’s public key ships inside every page. One access rule like using (true) and anyone holding it can read every row. In our study, anyone with the key could read personal data in 70 of 318 rebuilt apps.

02Unfixed

Scanners stop at a list.

A warning is where the work starts. Someone still has to write the policy, work out which pages depend on the old behaviour, and be sure real users are not locked out.

03Unproven

Nobody tests the fix before it ships.

A policy that looks right can still leak to signed-in strangers, or block owners from their own data. Without testing as each kind of user, you find out in production.

    Methodology

In the same run we scan your code and its full git history for exposed AI, payment and database keys.

Prove

A fix only counts when it passes three checks.

Every fix we hand over has been tested in the lab as three different people. If any check fails, it is not called proven.

Anonymous visitorDENIED
-- with your app's public key
select * from public.profiles;
→ 0 rows

Anyone on the internet has your public key; it ships inside your app. After the fix they read nothing.

Signed-in strangerDENIED
-- signed in as a different user
select * from public.profiles;
→ 0 rows

Anyone can create an account. Signing up must not unlock other people’s rows.

OwnerOK
-- signed in as the row's owner
select * from public.profiles;
→ 1 row, their own

A fix that locks real users out is not a fix. The owner must still read their own data.

supabase/migrations/20261109165700_patchlabs_leak_fix.sql
-- Fix: replace the "everyone can read" policy with owner-only access.
-- The old policy let anonymous and signed-in users read every
-- profile row, including email and phone.
DROP POLICY "Profiles are viewable by everyone" ON public.profiles;
CREATE POLICY "Users can view own profile" ON public.profiles
  FOR SELECT USING (auth.uid() = user_id);
Show the SQL behind the three checks

Simplified from what the lab runs. The test rows are fake; the identities are simulated inside the disposable database.

lab: three-identity proof
-- 1. anonymous visitor (anon key)
set local role anon;
select count(*) from public.profiles;  -- expect 0
-- 2. signed-in stranger
set local role authenticated;
select set_config('request.jwt.claims', '{"sub":"<stranger>"}', true);
select count(*) from public.profiles;  -- expect 0
-- 3. owner
select set_config('request.jwt.claims', '{"sub":"<owner>"}', true);
select count(*) from public.profiles;  -- expect their own rows
What “proven” does not cover

The proof covers the access rules we test, on the database your migrations build. If a migration is missing from the repo, or the app uses a backend other than Supabase/Postgres, the report says what could not be checked. It is not a guarantee that the whole app is secure.

Questions

Straight answers.

Something not covered? Email the founder and you’ll get a reply from the person who built it.

Isn’t Lovable’s or Supabase’s built-in check enough?

Use them: they are good at flagging common misconfigurations. They tell you a rule looks risky. They don’t rebuild your database and test, as each kind of user, whether a fix actually works. That proof is what we add. Detailed comparisons.

Do you touch my live database?

No. We work only from your GitHub repo and rebuild the database in a disposable lab with fake rows. We never connect to your live app or database, and the fix reaches production only when your engineer applies it.

What if the fix can’t be proven?

Then we don’t call it proven. The report says a person is reviewing it, and explains why. In our lab study 2 of 20 fixes went to a person. When a fix depends on a business choice, such as whether sellers’ emails should be public, the report asks you in plain English with a recommended answer.

Who approves the change?

You or your engineer. The fix is a migration file you download, or commit to your repo on GitHub in one click. Nothing changes until someone applies it. Automatic pull requests need our GitHub App, which is coming.

What do you keep?

Your email, the repo name, the report and the fix. The lab database is thrown away after each run. We never see your customers’ data because we never connect to your database. Signed-in users can export or delete everything we hold.

Is this a pentest?

No. A pentest is a person attacking your whole system within an agreed scope. We test one thing in depth: who can read which rows in your database, plus exposed keys in your code. For a high-stakes launch, get both.

Which apps does it work with?

Public GitHub repos with Supabase migrations in supabase/migrations: most Lovable, Bolt and Supabase projects, and many Replit and Cursor ones. Private repos come with our GitHub App.
