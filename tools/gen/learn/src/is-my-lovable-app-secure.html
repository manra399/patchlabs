How does a Lovable app keep its data private?

Lovable’s docs describe a built-in backend, enabled by default, and the option to connect your own Supabase project. This guide is about the database rules in Supabase-style projects, which is what PatchLabs tests. In these apps the browser code reads the database directly, using a public key. Row level security (RLS) is the set of per-table rules that decides what that key can read.

Lovable’s own docs call missing RLS policies the most common way app data gets exposed. So the question is whether the rules exist and whether they work. Lovable says schema migrations are saved as files under supabase/migrations/ in your project.

What are the six checks?

The times add up to about ten minutes.

Step 1: What does Lovable’s own scan say? (2 minutes)

Open the Security view in your project. Lovable’s docs say the Quick scan runs when you open the publish dialog and finishes in seconds. It reviews your database access rules and settings, npm dependency vulnerabilities and MCP servers exposed without authentication. The Deep scan reviews all application code and is started by you. Findings are marked Critical, Warning or Info. Fix the Critical ones first.

Lovable’s docs say the scans cannot guarantee complete security and suggest an additional professional review for sensitive data. That is why steps 2 to 6 exist.

Step 2: What does Supabase’s Security Advisor say? (1 minute)

In the Supabase dashboard, open the Security Advisor. You can also run supabase db advisors in the CLI. Supabase describes advisors as deterministic checks that ship with the platform. They flag tables without RLS and policies that are always true. Supabase’s docs add that some findings may be intentional, so read each one against what the table is for.

Step 3: Is RLS on for every table? (2 minutes)

Run this in the SQL editor to list every table in public and whether RLS is on.

rls-status.sql
-- Tables in public, with row level security on or off
select c.relname as table_name, c.relrowsecurity as rls_on
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind in ('r', 'p')
order by c.relrowsecurity, c.relname;

Any false is a table with no row rules. The full guide, how to check RLS on every Supabase table, explains how to read every result.

Step 4: Can a stranger read your data? (3 minutes)

RLS being on is not enough. A policy that says using (true) turns it back into an open door. Test the tables that hold personal data (profiles, customers, orders, messages, leads) as someone with no rights.

In the app, sign up a second account and look for the first account’s data. In SQL, run each table as the anon role, then as a signed-in stranger.

test-as-anon.sql
begin;
set local role anon;
select count(*) as anon_rows from public.profiles;  -- repeat for each table
rollback;

You want 0 for personal tables. A plain select in the editor is not a test: it usually runs as the postgres role, which owns your tables, and PostgreSQL’s docs say table owners normally bypass row security. The three-identity script covers the signed-in stranger and the owner.

Step 5: Is a secret key in your code? (1 minute)

Your Supabase URL and public key can be in the frontend. The service_role (or sb_secret_) key cannot, because it ignores every policy. Search the code and the history:

check-keys.sh
grep -rnE "service_role|SERVICE_ROLE|sb_secret_" --exclude-dir=node_modules .
git log --all --oneline -S"service_role"
# Any hit in src/ or in a VITE_ variable means it ships to the browser

You can also paste code into the free key check, which runs in your browser. If a secret key reached GitHub, rotate it first. Which keys are public: is the anon key safe?

Step 6: Who can sign up, and who is an admin? (1 minute)

  • Email confirmation is on, so nobody signs up with an address they don’t own (PL-018).
  • No policy decides access from user_metadata, which users can edit (PL-019).
  • The admin screen is backed by database rules, not only hidden in the browser (PL-020).

What does a pass look like?

Every table in public shows rls_on = true. Tables with personal data return 0 rows to anon and to a stranger, and the owner still sees their own rows. No secret key appears in the code, the bundle or the history. If something fails, fix it in a new migration and test again. Be precise when you ask Lovable, because a vague request can hide an error without closing the leak. The fix is in how to secure a Lovable app’s Supabase database.

Questions people ask

Is Lovable safe for a production app?

Lovable generates the code, and the app’s security depends on its database rules, keys and sign-up settings. Lovable’s docs say its scans cannot guarantee complete security, so check the six items above before real users arrive.

Does Lovable’s security scan guarantee my app is secure?

No, and Lovable’s docs say so. The Quick scan runs a fixed set of checks in seconds. The Deep scan reads all application code. Neither is a substitute for testing who can read your tables as an outsider.

How do I know if my Lovable app’s database is public?

Run the anon test in step 4 on every table that holds personal data. If it returns rows, anyone with your public key can read them. About 22% of the apps in the PatchLabs study (70 of 318) were readable that way.

Can I check a Lovable app without sharing my code?

Yes. The SQL checks run inside your own Supabase project, and the free key check runs in your browser without uploading anything. The free RLS check reads a public GitHub repo.
