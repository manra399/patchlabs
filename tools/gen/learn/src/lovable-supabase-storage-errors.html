This guide is for founders and agencies with a Lovable app (or any Supabase app built with Bolt, Cursor or Claude Code) where uploads fail, a file is rejected as too large, or Supabase has emailed about the storage quota. The results come from our own run on 24 November 2026: Supabase’s open-source Storage server (supabase/storage-api 1.98.5, local file backend) on Postgres 17.11, a private bucket called uploads, two fake users (Alice and Bob) and a logged-out visitor holding only the public key. They show the pattern, not any particular app. The scripts are short and we can share them.

Which error do you have?

Open your browser’s developer tools, try the upload again, and read the response of the request to /storage/v1/object/…. The message is the same one supabase-js returns in error.message.

What you seeCause
new row violates row-level security policyNo policy on storage.objects lets this user upload to this bucket and path. Cause 1.
The object exceeded the maximum allowed sizeThe file is over the bucket’s limit or the project’s global limit (50 MB at most on Free). Cause 2.
Bucket not foundThe bucket name in the code doesn’t match a bucket, or the code asks for a public URL from a private bucket. Check the name; don’t make the bucket public to fix it.
Uploads still work, but Supabase emails that you are over the storage quotaYour organisation is over its plan’s storage size. Cause 3.

Cause 1: no storage policy allows the upload

A new private bucket has no policies, so the Storage API refuses every upload, even from a signed-in user uploading into their own folder. In our run, Alice’s first upload got:

[[CODE lab output, 24 Nov 2026]] alice upload: {"statusCode":"403","error":"Unauthorized", "message":"new row violates row-level security policy"} [[/CODE]]

That refusal is the safe default. The fix is a policy that lets each user write only their own files (below), not a policy that lets everyone write everything.

Cause 2: the file is over the size limit

Every file is checked against the bucket’s own limit, if it has one, and the project’s global limit. On the Free plan the global limit can’t go above 50 MB; on Pro and above it can be set up to 500 GB. We set a 1 MB bucket limit and uploaded 2 MB as a user who was allowed to upload:

[[CODE lab output, 24 Nov 2026]] alice 2 MB upload: {"statusCode":"413","error":"Payload too large", "message":"The object exceeded the maximum allowed size"} [[/CODE]]

Raise the bucket’s limit under Storage settings, or compress or resize the file in the browser before upload. Nothing about this error needs a policy change. If the AI builder’s answer touches row level security, it is fixing the wrong problem.

Cause 3: the storage quota

The quota is the total size of every file in every bucket across your organisation: 1 GB on the Free plan, 100 GB on Pro, then $0.0213 per GB per month above that. Supabase measures it in GB-hours, so the figure it compares with your quota is the average over the billing period, not today’s size. Deleting 500 MB today lowers the month’s average a little each day, not all at once.

To see what is using the space, run this in the SQL editor. It only reads:

[[CODE storage-size.sql]] select b.id as bucket, b.public, b.file_size_limit, count(o.id) as files, pg_size_pretty(coalesce(sum((o.metadata->>'size')::bigint), 0)) as total_size from storage.buckets b left join storage.objects o on o.bucket_id = b.id group by b.id, b.public, b.file_size_limit order by coalesce(sum((o.metadata->>'size')::bigint), 0) desc; [[/CODE]]

Don’t free space by deleting rows in SQL

An AI builder will often suggest delete from storage.objects where …. Each row in that table only points at a file; the file itself lives in Supabase’s object store. Supabase now blocks the delete with a trigger, and our run hit it:

[[CODE lab output, 24 Nov 2026]] delete from storage.objects where bucket_id = 'uploads'; ERROR: Direct deletion from storage tables is not allowed. Use the Storage API instead. [[/CODE]]

The trigger can be switched off with a setting (storage.allow_delete_query), and some answers online do that. We did it to see what happens: the row went, and the file stayed on disk with nothing pointing at it.

[[CODE lab output, 24 Nov 2026]] files on disk before: 1 with storage.allow_delete_query=true: deleted 22222222-…/passport.txt rows left: 0 files on disk after: 1 [[/CODE]]

Delete files in the Storage page of the dashboard, or with supabase.storage.from('uploads').remove([...]) from a server using the service key. In our run, Alice deleting her own file through the API, with the policies below, returned “Successfully deleted” and removed the file.

The two quick fixes that expose every file

Paste the upload error into an AI builder and these are the two answers you are most likely to get. We applied each one to a fresh bucket that held one file of Bob’s (fake passport details), then tried it as Alice and as a logged-out visitor.

Quick fix A: make the bucket public

[[CODE do not ship]] update storage.buckets set public = true where id = 'uploads'; [[/CODE]] [[CODE lab output, 24 Nov 2026]] alice upload: "new row violates row-level security policy" still broken anon GET /object/public/uploads//passport.txt: 200 Bob Example, passport 123456789 (fake test data) anon list: 0 files [[/CODE]]

This doesn’t even fix the upload: public only affects downloads. It does make every file downloadable by anyone with its URL, with no sign-in, forever. Listing stayed closed, so a stranger needs the path, but paths built from a user id and a file name are shared in links, logs and screenshots. That is fine for logos and wrong for ID scans, invoices or anything personal. This is finding PL-007.

Quick fix B: a policy “for all” that checks only the bucket

[[CODE do not ship]] create policy "Allow all" on storage.objects for all using (bucket_id = 'uploads') with check (bucket_id = 'uploads'); [[/CODE]] [[CODE lab output, 24 Nov 2026]] alice upload: 200 upload works anon list bob's folder: 1 ['passport.txt'] anon download bob's file: 200 Bob Example, passport 123456789 alice overwrites bob's file (upsert): 200 bob's file now says: replaced by alice anon deletes bob's file: 200 "Successfully deleted" [[/CODE]]

A policy with no to clause applies to every role, including the logged-out visitor, and a policy that checks only bucket_id covers every file in the bucket. Together they let anyone with your public key list, download, replace and delete every user’s files. Writing to authenticated closes the door to logged-out visitors but still lets any user who signs up do all of the above to everyone else. This is finding PL-015.

The fix that keeps uploads working and files private

Keep the bucket private and upload each user’s files under a folder named after their user id, for example supabase.storage.from('uploads').upload(`${user.id}/${file.name}`, file). Then one migration:

[[CODE supabase/migrations/…_storage_per_user.sql]] -- 1. Undo the quick fixes, if they were applied update storage.buckets set public = false where id = 'uploads'; drop policy if exists "Allow all" on storage.objects; -- 2. Each signed-in user can only touch files in their own folder create policy "uploads: own folder insert" on storage.objects for insert to authenticated with check (bucket_id = 'uploads' and (storage.foldername(name))[1] = (select auth.uid()::text)); create policy "uploads: own folder read" on storage.objects for select to authenticated using (bucket_id = 'uploads' and (storage.foldername(name))[1] = (select auth.uid()::text)); create policy "uploads: own folder update" on storage.objects for update to authenticated using (bucket_id = 'uploads' and (storage.foldername(name))[1] = (select auth.uid()::text)) with check (bucket_id = 'uploads' and (storage.foldername(name))[1] = (select auth.uid()::text)); create policy "uploads: own folder delete" on storage.objects for delete to authenticated using (bucket_id = 'uploads' and (storage.foldername(name))[1] = (select auth.uid()::text)); [[/CODE]]

What our run showed after it:

[[CODE lab output, 24 Nov 2026]] alice upload own folder: 200 uploads work alice re-upload (upsert): 200 replacing her own file works alice upload into bob's folder: "new row violates row-level security policy" alice reads bob's file: "Object not found" alice overwrites bob's file: "new row violates row-level security policy" alice deletes bob's file: "Access denied" anon list bob's folder: 0 files anon public URL: "Bucket not found" bob reads own file: 200 [[/CODE]]

To show a private file in the page, create a short-lived signed URL (createSignedUrl(path, 60)) instead of a public one. If users need to share files with each other, add a policy for that case on purpose, for example by checking a shares table, rather than widening the folder rule. Our storage bucket policies guide covers public and private buckets, shared files and signed URLs in more detail.

Check which state your app is in

Run this in the Supabase SQL editor. It changes nothing.

[[CODE check-storage-policies.sql]] select policyname, cmd, roles, 'public' = any(roles) as applies_to_everyone, coalesce(qual, '') || coalesce(with_check, '') not like '%auth.uid()%' as not_per_user from pg_policies where schemaname = 'storage' and tablename = 'objects' order by policyname; [[/CODE]]
ResultMeaning
applies_to_everyone trueThe policy has no to clause, so logged-out visitors get it too. On a select, update or delete policy that is quick fix B.
not_per_user trueThe policy doesn’t look at who is signed in, so it covers every user’s files. Fine for a deliberately public bucket of logos; wrong for anything personal.
a bucket with public true in the size queryEvery file in it can be downloaded by URL with no sign-in. Make sure nothing personal is in it.
no rowsNo storage policies at all: uploads will fail until you add the per-user ones.

In our run the query flagged quick fix B on both columns and passed all four per-user policies.

Tell your AI builder the rule

[[CODE prompt for Lovable or your AI builder]] File uploads fail with "new row violates row-level security policy". Do not make the bucket public and do not add a storage policy that checks only bucket_id or has no TO role. Fix it like this: - Keep the bucket private. Upload to `${user.id}/${fileName}`. - Add insert, select, update and delete policies on storage.objects TO authenticated, each requiring bucket_id = '' and (storage.foldername(name))[1] = (select auth.uid()::text). - Show files with createSignedUrl, not getPublicUrl. - Never delete rows from storage.objects in SQL; use storage.remove(). Show me the migration before applying it. [[/CODE]]
