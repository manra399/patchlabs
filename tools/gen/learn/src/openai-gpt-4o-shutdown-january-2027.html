This guide is for founders whose app uses OpenAI, especially apps built with Lovable, Bolt, Replit or Cursor, where nobody may remember which model the AI picked. Every date here comes from OpenAI’s deprecations page, read on 14 November 2026. The search command was tested by us on that date against a sample project.

What shuts down, and when

OpenAI gives each model one of three states: active, deprecated (retirement announced, still works) and shut down (“no longer accepts requests through the standard API”). These are the shutdowns in the next three months:

Shuts downModel → replacement
30 Nov 2026Reusable prompt objects (/v1/prompts), Agent Builder
→ Prompt text in your own code; Agents SDK
11 Dec 2026gpt-5, gpt-5-mini, gpt-5-nano, gpt-5-pro, o3, o3-pro
→ gpt-6.1-sol, gpt-6.1-terra (for mini), gpt-6-luna (for nano)
6 Jan 2027tts-1, tts-1-hd, gpt-4o-mini-tts
→ gpt-realtime-2.1-mini
14 Jan 2027gpt-4o-2024-08-06, gpt-4o-2024-11-20, gpt-4o-mini-2024-07-18, gpt-4.1-2025-04-14, gpt-4.1-mini-2025-04-14
→ gpt-6-luna
20 Jan 2027gpt-realtime, gpt-audio and the 4o audio and realtime models
→ gpt-realtime-2.1, gpt-audio-1.5

Two things that catch people out. Fine-tuned models stop on the same day as the model they were trained from. And some models are already gone: gpt-4.1-nano, gpt-4o-2024-05-13, o4-mini, gpt-4-turbo and gpt-3.5-turbo shut down on 23 October 2026, and the Assistants API on 26 August 2026. If your app uses one of those, the feature is failing now.

Only 92 days’ notice. OpenAI’s own policy promises at least six months for generally available models “unless safety or compliance concerns require a faster timeline”. The GPT-4o notice went out on 14 October for 14 January, so there’s less time than usual.

What about plain “gpt-4o”?

Most apps don’t ask for gpt-4o-2024-11-20. They ask for gpt-4o, a name that points at whichever snapshot OpenAI chooses. OpenAI’s table lists the snapshots by date and doesn’t list the bare name, so the page doesn’t say what gpt-4o will do on 15 January. Every snapshot it has pointed at is on the list. Plan as if it stops working, and don’t count on it being moved to a newer model for you: even if it were, your replies would change without you choosing it.

Find the model name in your app

The model is a plain string, so it can be anywhere: in code, in .env, in your host’s environment settings, or in a Supabase secret. In Lovable and Bolt apps the call to OpenAI usually lives in a Supabase Edge Function (supabase/functions/<name>/index.ts), because the key mustn’t be in the browser. From the project folder:

[[CODE terminal]] grep -rnoE --exclude-dir={node_modules,.git,dist,build,.next} \ "\b(gpt-4o|gpt-4\.1|gpt-5(\.1)?|o3|tts-1|whisper-1|gpt-realtime|gpt-audio)[a-z0-9.-]*" . \ | grep -vE ":gpt-5\.[2-9]|:gpt-6" [[/CODE]]

Each line is a file, a line number and the model name it found. We ran it on a sample project with the name in an Edge Function and in .env: it found gpt-4o, gpt-4o-mini-tts, o3, gpt-4.1-mini, gpt-5 and gpt-5.1 (which goes on 1 April 2027), and skipped gpt-6-luna and words like demo3. Then check the places grep can’t see:

  • Supabase: Project Settings, Edge Functions, Secrets. Look for anything like OPENAI_MODEL.
  • Vercel, Netlify, Railway, Render: the project’s environment variables page.
  • No-code tools (Make, Zapier, n8n, Bubble): the OpenAI step has a model drop-down. Open each scenario that calls OpenAI.

No terminal? Paste the files and your .env into the free model shutdown check. It runs in your browser and lists every model on OpenAI’s shutdown list, with the days left.

Switch without breaking the feature

Changing one string is the easy part. A newer model can format answers differently, ignore an instruction the old one followed, take different parameters or cost a different amount. OpenAI’s own advice is to run representative requests against both models and compare before moving production traffic. For a small app that means:

  1. Make the model one setting. Put the name in one environment variable (for example OPENAI_MODEL) and read it everywhere. The next shutdown becomes a one-line change.
  2. Collect ten real inputs. Pick prompts your users actually send, including the long and awkward ones.
  3. Run both models on them before 14 January, while the old one still answers, and read the replies side by side. Check anything your code parses: JSON fields, lists, word limits.
  4. Watch the error path. Make sure a failed call shows the user a message and writes a log line. Many AI-built apps catch the error and show an empty reply, which is how a shutdown goes unnoticed for days.
  5. Switch, then check the bill after a day of real traffic.

Paste this into your AI builder with the project open:

[[CODE prompt for Lovable, Bolt, Cursor or Claude]] OpenAI shuts down gpt-4o, gpt-4o-mini, gpt-4.1 and gpt-4.1-mini on 14 January 2027 (and o3, gpt-5 and gpt-5-mini on 11 December 2026). 1. Find every place this app names an OpenAI model, including Edge Functions and environment variables, and list them. 2. Replace them with one setting, OPENAI_MODEL, read from the environment, defaulting to gpt-6-luna. 3. Make sure every OpenAI call shows the user a clear message and logs the error if the call fails, instead of showing an empty reply. 4. Don't change prompts or other behaviour. Show me the diff before applying it. [[/CODE]]

Catch the next one

OpenAI adds shutdowns every few months, and the notice email goes to whoever owns the API account, which for an app built for you may be the agency or freelancer, not you. Three cheap habits:

  • Make sure the email on your OpenAI organisation is one you read.
  • OpenAI’s List models endpoint (GET /v1/models) and Retrieve model endpoint return an optional shutdown_date for each model. A small scheduled job that checks your model and alerts you when that field appears catches the next notice on the day it lands.
  • If you call OpenAI through Azure, Microsoft runs its own retirement schedule with different dates; check its model retirement page as well.
