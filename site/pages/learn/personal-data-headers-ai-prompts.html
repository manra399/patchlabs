Keys and incidents

Your users’ personal data is probably in your headers and your AI prompts. Here’s where it ends up.

Most leaks we write about are a database table anyone can read. This one is quieter. A request header that carries a user’s email, or a prompt that carries a customer’s address and date of birth, gets copied into logs, traces and vendor storage that you never look at and can’t delete. The Uber breach disclosed this month is a reminder of what that costs: driver records held at an AI vendor were taken when the vendor was breached. Here’s where the copies go, how to find them in your code in a minute, and what to send instead.

By Manraj Singh Dhillon, technical founderChecked 16 Nov 20264 min read

TL;DR

  • Uber told US state attorneys general that names, addresses, dates of birth and driver’s licence numbers of 149,346 people were taken from data it had stored with Fireworks AI, after attackers stole Fireworks’ own internal credentials (as reported by TechCrunch on 16 November 2026).
  • Anything you send in a request header can be written to CDN, proxy, load balancer and APM logs, which are kept for weeks or months and read by more people and vendors than your database.
  • Anything you put in a prompt is stored by the AI provider for abuse monitoring, and often again by a gateway, tracing or eval tool in between.
  • Send an opaque user id in headers, never an email or phone number. Send the model only the fields the task needs, mask the rest, and never JSON.stringify a whole user record into a prompt.
  • Our free, open-source CLI flags both (finding PL-037): uvx --from git+https://github.com/manra399/patchlabs-cli patchlabs scan .

This guide is for founders and agencies shipping apps built with Lovable, Bolt, Cursor or Claude Code, especially apps that call an AI model with customer data. The Uber facts come from TechCrunch’s report of 16 November 2026, which cites Uber’s breach notices to state attorneys general. We have no inside information, and the report doesn’t say how Uber used the data it stored with Fireworks.

What the Uber notice says

The lesson for a small team isn’t “don’t use AI vendors”. It’s that every copy of personal data you hand to another system is a copy you can no longer protect. Your database can have perfect row level security and the same email address can still sit in five other places.

Where a header goes

AI builders often fix “the server doesn’t know who’s calling” by adding a header. It works on the first try, so it stays:

src/lib/api.ts (risky)
const res = await fetch("/api/orders", {
  headers: {
    "Content-Type": "application/json",
    "X-User-Email": user.email,   // copied into every log on the way
    "X-Phone": user.phone,
  },
});

Between the browser and your function, that request can pass through a CDN, your host’s edge network, a load balancer and your own logging or APM tool. Several of these can record request headers, and they keep them for weeks or months. Those logs are read by your team, your host’s support staff and every tool you have connected to them. None of them has your database’s access rules. A header is also easy to forge: anyone can send X-User-Email: someone-else@…, so a server that trusts it has a second problem (see PL-022).

Send instead: nothing. Your function already gets the signed-in user from the session token (supabase.auth.getUser() in an Edge Function or API route) and can look the email up itself. If a header must identify someone, use an opaque id such as the user’s UUID, never an email, phone number or ID number.

Where a prompt goes

The same thing happens with AI features. The fastest way to give a model context is to paste the whole record in:

supabase/functions/summarize/index.ts (risky)
const completion = await openai.chat.completions.create({
  model: "gpt-5-mini",
  messages: [
    { role: "system", content: "You write short care summaries." },
    { role: "user", content: `Patient ${patient.full_name}, born ${patient.date_of_birth}` },
    { role: "user", content: JSON.stringify(profile) },   // every column, including ones you added later
  ],
});

Each prompt can be kept in several places: the model provider’s own storage for abuse monitoring (how long depends on the provider and your account settings), any AI gateway or router you send it through, and any tracing, logging or eval tool you’ve wired in. JSON.stringify(profile) is the worst version, because it quietly sends every column you add to the table later, such as a phone number or an ID document field.

Send instead: only the fields the task needs. Replace names, emails and numbers with placeholders such as [NAME] before the call and put them back in the answer afterwards, if the answer needs them at all. Then check your provider’s data retention and training settings for your account, and whether your tracing tool stores prompt text.

supabase/functions/summarize/index.ts (fixed)
const notes = redact(patient.visit_notes);   // strip names, emails, phone and ID numbers
const completion = await openai.chat.completions.create({
  model: "gpt-5-mini",
  messages: [
    { role: "system", content: "You write short care summaries. Refer to the person as [PATIENT]." },
    { role: "user", content: notes },
  ],
});
const summary = completion.choices[0].message.content.replaceAll("[PATIENT]", patient.first_name);

Find it in your code in a minute

Our command-line scanner is free and open source. It reads your repository as text, never runs it and sends nothing anywhere. From version 0.4.0 it flags both patterns as PL-037: a header whose name or value carries a personal field or a real email address, and a prompt line near an OpenAI, Anthropic, Gemini, Vercel AI SDK or LangChain call that includes a personal field or a whole user record. It reads JavaScript, TypeScript and Python.

terminal
uvx --from git+https://github.com/manra399/patchlabs-cli patchlabs scan .

ID, health, card and bank fields are rated high, contact fields (email, phone, address, date of birth, name) medium. Opaque ids, example.com addresses, commented-out lines and the code that reads the model’s answer are not flagged. Before release we ran it on ten real repositories, including three open-source AI chat apps and cal.com: none was flagged, and reading their code by hand, none sends personal fields to a model or puts them in a header.

Prefer to look by hand? These two searches find most cases:

check.sh
# headers that carry personal data
grep -rnE "['\"]X-[A-Za-z-]*(Email|Phone|Name|Address|Dob)['\"]" --exclude-dir=node_modules .

# whole records sent to a model
grep -rnE "JSON\.stringify\((user|profile|customer|patient)" --exclude-dir=node_modules .

When it’s fine

Sometimes the model genuinely needs a personal detail: an assistant that drafts an email to a named customer, say. That can be a sound decision. Make it on purpose: write down which fields go, check the provider’s retention terms, tell users in your privacy notice, and keep the fields out of your tracing tool. The finding is there so the decision is made by a person, not by whatever the AI builder wrote first.
