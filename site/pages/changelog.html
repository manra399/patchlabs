25 Nov 2026shipped

Your code is deleted the moment a check ends, and a daily cap on model spend.

Groundwork before our first paying agencies.

  • Changed

    Your repo’s code is deleted as soon as its check ends

    The worker now removes its copy of your code the moment a check finishes, pass or fail, instead of keeping it up to 30 days. The report, findings and fix stay up to 30 days so a person can review an unclear result. The worker’s disk is encrypted. Privacy, data processing terms and Security say the same.

  • New

    A daily cap on fix-agent spend

    If a day’s model spend reaches the cap, new checks wait in the queue until midnight UTC and the founder is emailed. Nothing is dropped.

24 Nov 2026shipped

Two guides for broken Lovable apps: storage errors, and contact forms that fail on submit.

The second guide written from what people search for when they reach us.

  • New

    Guide: contact form fails with a row-level security error

    Reproduced on Postgres 17 with PostgREST 12.2.12 and Supabase’s default grants: with an insert-only policy, .insert(row).select() fails with “new row violates row-level security policy” because reading the row back needs select. The three usual fixes all made the form work and all let a logged-out visitor read every submission; two also let them delete every row. The guide has the fix we proved (no .select(), column-level insert grant, admin-only read) and a read-only query that lists anon-readable tables. Read the guide.

  • New

    Guide: Lovable storage errors and the storage quota

    Failed uploads, “The object exceeded the maximum allowed size” and the storage quota, reproduced on Supabase’s open-source Storage server (1.98.5) on Postgres 17. A policy “for all” that checks only the bucket fixed the upload and let a logged-out visitor list, download and delete another user’s file; a public bucket served it to anyone with the URL. Deleting rows in SQL to free space left the file on disk. The guide has the per-user folder fix (uploads work, stranger and visitor get nothing) and a read-only query for your policies. Read the guide.

23 Nov 2026shipped

The revert test, 36 hours on, our sign-in form closed to bots, and a guide to Lovable sign-up errors.

A follow-up to yesterday’s test of what a revert leaves behind, and a new guide.

  • New

    Guide: Lovable sign-up errors, fixed without opening your data

    “Database error saving new user” and “new row violates row-level security policy” are the two database errors that usually break sign-up in a Lovable app. We reproduced both on Postgres 17, then applied the two quick fixes an AI builder usually suggests: with row level security off, or with policies that say true, a logged-out visitor read every user’s email and phone number. The guide has the one-migration fix (sign-up works, visitor and stranger read 0 rows, owner 1) and a read-only query that tells you which state your app is in. Read the guide.

  • Updated

    Guide: a revert is not a rotation

    We re-checked the demo token 36 hours after the force-push, without signing in: the commit page (full, 7- and 4-character id), the raw file and the REST API all still return it. We also found that the repo’s public Activity page and /activity API list the force-push with the full id of the commit it removed, so nobody needs to guess. Read the updated section.

  • Fixed

    Our sign-in form can no longer be used to email strangers

    Reading our own logs, we found a bot had been typing other people’s addresses into the sign-in form since 10 Nov, about one an hour from different networks, so about 45 people got a PatchLabs sign-in link they never asked for (sorry). Three of those links were opened by company mail scanners within 30 seconds, which created empty accounts. Now the form needs a signed one-time challenge with a small proof of work and a short wait, a hidden field catches form-filling bots, links to brand-new addresses are capped per hour, and a link only signs in when a person clicks Continue. Nothing else was reached: the accounts held no apps or data. API change.

  • New

    FAQ: can the fix agent change the test it’s graded by?

    An engineer asked us this, so the answer is now on How it works: the tests live in our lab, the agent can only call the verifier, and the proof that counts is a second run the pipeline does by itself after the agent stops.

  • Fixed

    Third-party script finding no longer cut short

    The incident note on PL-040 was cut off at 300 characters, ending mid-word. Evidence now keeps up to 500.

22 Nov 2026shipped

A new check for hijacked third-party scripts, two guides updated for this week’s incidents.

A new free check and a new guide after the Optimizely compromise, plus updates tied to two incidents reported this week.

  • New

    PL-040 in the free headers check

    On 16 Nov, code injected into Optimizely reached visitors of at least 178 organisations from Optimizely’s own CDN. The headers check now lists the scripts a page loads from other sites and flags it when no Content-Security-Policy limits where they can send data (connect-src and img-src, or default-src). It rises to medium when a script host had a public compromise in the last 90 days. The same check runs in the API, the MCP headers_check tool and the Apify Actor. PL-040 explained.

  • New

    Guide: a script you trust was hijacked

    What happened at Optimizely, a console snippet that lists every outside script your app runs, and a Chrome test of what a policy really stops: with only a script-src allow-list, a script still sent data out four ways; with default-src 'self', none got out. Read the guide.

  • New

    Comparison: PatchLabs vs Keybrum

    Keybrum launched on 22 Nov: it attacks your live app and gives your coding agent a fix prompt. We compared it with PatchLabs from its public pages, including where it is the better choice (live-app coverage, a €49 one-off report, more apps per plan). Read the comparison.

  • Updated

    Guide: a revert is not a rotation

    On 21 Nov, Together AI disclosed that an AI coding agent committed a credential to a public repo; it was reverted, and prompt samples were still downloaded. We tested what a revert leaves on GitHub: even after a force-push removed the commit from every branch, a stranger with no login could read the token from the first four characters of the commit id. Read the test.

  • Updated

    Guide: the credit union case

    BleepingComputer reported on 18 Nov that payee records from about 40 Irish credit unions were exposed when an attacker with a valid login ran a script that made five million requests against an authorization flaw. The two-account guide now explains what that means for an AI-built app: a signed-in user proves nothing, one leaking request means every row, and without logs you cannot say who was affected. Read the section.

18 Nov 2026shipped

Code checks catch logins that store passwords in plain text.

One new check in the free CLI and the hosted Code check, from the same code.

  • New

    Passwords stored or looked up in plain text (PL-039)

    Some AI-built logins skip the auth service and keep their own users table: they save the password as typed and log people in with a query like .eq("password", password). The check flags a query that matches on the password, an insert that saves a bare password in a repo that never hashes one, and a plain password column. It ignores auth-provider calls, hashed values and frameworks that hash for you. Checked on ten real projects that handle passwords properly, including cal.com, Payload and Directus, with no false alarms, and it flagged all six sampled public repos that use the pattern.

17 Nov 2026shipped

Code checks catch personal data sent to AI models, and a leak must be shown before we call it one.

Changes to every hosted check, and a promise that the free CLI and the hosted check stay the same.

  • New

    Personal data in request headers or AI prompts (PL-037)

    Flags emails, phone numbers and ID numbers put in request headers, and prompts near an OpenAI, Anthropic, Gemini, AI SDK or LangChain call that paste in personal fields or a whole user record. JavaScript, TypeScript and Python. Checked against ten real open-source repos, including three AI chat apps and cal.com, with no false alarms.

    PL-037The guide
  • New

    Claude Code settings files with keys (PL-009)

    The hosted check now also reads .claude/settings.local.json and .claude/settings.json, where allow rules and env blocks often hold live keys.

    The guide
  • Changed

    “Proven” now starts with the leak being shown

    Before a finding counts, the lab seeds rows and reads them as an anonymous visitor and a signed-in stranger with no fix applied. A table that only looks open is reported as unproven and never sent to the fix agent, and a fix only passes if the leak was reproduced first.

    How it works
  • Changed

    The free CLI and the hosted check now run the same code checks

    The hosted Code check used to keep its own copy of the checks, and it fell behind the free CLI. Now its checks are copied from the open-source patchlabs-cli at a pinned release, a test fails if anyone edits that copy by hand, and we compare it with the latest CLI every six hours. If the free CLI finds something in your repo, a paid check finds it too.

    patchlabs-cli on GitHubPatchLabs Code
  • New

    Teams and organisations: anyone joining any team (PL-038)

    Multi-tenant apps often say “you can see this row if you are a member of its team”. If a signed-in user can insert their own row into the members table, or move it to another team, they join any team and read its data. The free RLS check and patchlabs-cli now find the members tables your other rules rely on, directly or through a helper such as is_member(), and flag write rules that only check “the row is mine”. Proven on Postgres 17: an outsider read 0 rows, added themselves, then read every customer row; the admin-check fix refused it.

10 Nov 2026v3 · shipped

PatchLabs v3: four product lines, and checks that read your code.

v2 found who could read your database. v3 adds a second engine that reads the rest of your repo, puts every result in one finding format, and organises PatchLabs into four product lines.

  • New

    Four product lines

    Lab rebuilds your database from its migrations and reproduces each leak as an anonymous visitor, a signed-in stranger and the owner. Code reads the repo. Fix writes the migration, proves it and waits for your engineer. Watch re-checks, diffs, alerts and signs every result. Old product URLs redirect to the new ones.

    LabCodeFixWatch
  • New

    PatchLabs Code: new checks on every run

    Reads the repo without running it or installing anything, and reports with a file and line: secret keys in the current code (PL-009), Edge Functions open without sign-in while using the service key (PL-017), sign-ups without email confirmation (PL-018), access decided by user_metadata (PL-019), admin checks only in the browser (PL-020), payment webhooks that don’t verify signatures (PL-021), functions that trust a user id from the request (PL-022), dependencies with known vulnerabilities from OSV (PL-023), user content rendered as raw HTML (PL-024), open Firebase rules (PL-025) and risky CORS (PL-026). The dependency check sends only package names and versions to OSV, and is reported as skipped when OSV can’t be reached.

    Finding index
  • New

    One finding format

    Every finding, from the Lab or Code, has the same fields: ID, line, severity, object, file and line, redacted evidence, whether it was proven, the proof and a one-line fix. The report groups findings by line, and a finished check’s API summary carries the list and counts by severity.

    The format
  • New

    Findings library and guides

    A page for every finding ID from PL-001 to PL-026, each with vulnerable code, a self-check and the fix, and filters by line, severity and status. Plus a Learn section of in-depth guides: RLS with stranger tests, roles and user_metadata, Edge Functions, Stripe webhooks, storage, views, Realtime, leaked keys, Firebase rules, dependencies and a pre-launch checklist.

    Learn
  • New

    A demo you can click through, and a rebuilt site

    The real app on a fake demo workspace, clearly labelled, with no sign-in. A rebuilt home page, a products menu, integrations and pages for founders, agencies and the engineers who approve fixes.

    Try the demoIntegrations

Not in v3: five new Lab checks are written up but not tested yet: strangers changing other people’s rows (PL-012), users making themselves admin (PL-013), views skipping RLS (PL-014), open storage policies (PL-015) and Realtime streams (PL-016). Their pages say so, and they won’t appear in reports until they ship. Automatic pull requests still need the GitHub App, which is coming.

Measured effect: too new to measure. We’ll add numbers here once enough checks have run with the new code checks to report them honestly.

PatchLabs v2: accounts, monitoring and proof anyone can verify.

v1 checked an app once. v2 keeps watching it: sign in, add your apps, and we re-check them on a schedule, tell you what changed and sign every result so anyone can verify it.

  • New

    A new website

    A rebuilt patchlabs.dev in a light and dark “lab notebook” design, with pricing, fair comparisons, docs and research. Every page works without JavaScript. No cookies, no third-party analytics.

  • New

    Accounts and workspaces

    Sign in with a one-time email link; there are no passwords. Your first sign-in creates a workspace and links earlier checks made with the same email. Invite teammates as owners or members. Export everything we hold about you, or delete your account, from Settings.

    Sign in
  • New

    Monitoring

    Add an app, prove it’s yours once, and it’s re-checked weekly or monthly. “Run now” any time. Each check shows what’s new, what’s fixed and what’s still leaking since the last one. Every member gets an email (the subject says “new leak” when there is one) and your webhook gets a one-line summary that works as a Slack incoming webhook.

    MonitoringWebhooks
  • New

    Badges and public status

    An opt-in SVG badge for your README or site: “no known leaks”, “fix in progress” or “not checked yet”, with the date of the last check. It links to a public status page that shows the repo, status and date, and nothing exploitable.

    Badge & proof page
  • New

    Signed receipts

    Every finished check gets a receipt signed with Ed25519: the repo, status, leaking tables, whether the lab proof passed, a hash of the fix, and every owner decision. Our public key is published at /.well-known/patchlabs-receipt-key on the API, so anyone can check a receipt hasn’t been changed.

    Verify a receipt
  • New

    Owner decisions and answers

    Approve a fix, or mark a table as meant to be public. We remember that choice for the app and stop alerting on it. Answers to the report’s plain-English business questions are saved too, and both go into the signed receipt.

  • New

    REST API and API keys

    Create workspace keys (pl_live_…, shown once, stored hashed) and start a check from CI with POST /v1/apps/{id}/checks. Errors are always a plain sentence.

    API reference
  • New

    Remote MCP server

    Point Cursor, Claude Code or any MCP client at https://api.patchlabs.dev/mcp. Tools: rls_check, start_check and get_check for anyone; list_apps and run_check with your workspace key.

    Set up MCP
  • New

    Free RLS check, no sign-up

    Paste a public repo and get a static read of its supabase/migrations in seconds: which tables have row-level security, their policies, columns that look personal, and eight finding types from PL-001 (anon can read personal data) to PL-008 (RLS never enabled). Static analysis only; the full check proves it in the lab.

9 Nov 2026v1

First public leak checks.

Anyone can paste a public repo and get a report: what a stranger can read, the fix, and the proof that it works.

  • New

    Public leak checks

    Paste a public GitHub repo and your email. Prove the repo is yours by committing patchlabs-verify.txt with a one-time code. The lab rebuilds your database from supabase/migrations in a disposable Postgres with Supabase’s roles, auth functions and default grants, seeds fake rows, reads as an anonymous visitor and a signed-in stranger, writes the fix and proves it. It never connects to your live app or database.

    See a sample report
  • New

    Reports by email

    The report link is emailed to you when the check finishes, so you can close the tab.

  • New

    A spend cap on every check

    The smallest Claude model writes the fix first. A larger model is used only if the lab proof fails, and every check has a hard spend cap.

  • Study

    18 of 20 fixes proven with no human help

    We ran the autonomous pipeline on 20 new apps. 18 of 20 fixes passed the strict lab proof with no person involved; 15 needed only the smallest model. The other 2 went to a person. Corrected 24 Nov 2026: re-checked with our stricter current verifier, 17 of 20 pass and 14 on the smallest model; one fix had never been tested against a real row.
