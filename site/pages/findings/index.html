Data access · who can read what

PL-001

Anonymous visitor can read personal data

Anyone with your app's public key can read emails, phone numbers or addresses.

criticalRLS check · lab→ PL-002

Any signed-in user can read every row

Signing up unlocks other people's rows. If sign-up is open, that means anyone.

highRLS check · lab→ PL-003

RLS enabled but no policies (owner locked out)

Not a leak, yet. The table is locked to everyone, and the quick fix people reach for is the leak.

lowRLS check · lab→ PL-004

UPDATE policy missing WITH CHECK

Users may edit their own row, and nothing stops them changing its role, plan or owner.

mediumRLS check→ PL-005

Always-true policy

A policy that says yes to everyone. On writes, anyone can change or delete your data.

high to lowRLS check · lab→ PL-006

SECURITY DEFINER function exposed

A function that runs with the owner's powers, callable by anyone through the API.

high or mediumRLS check→ PL-007

Public storage bucket

Files in this bucket are served to anyone with the link. ID scans and invoices don't belong there.

mediumRLS check→ PL-008

Row level security not enabled

No rules at all. With API access granted, anyone with the public key can read and change every row.

Severity

Ranked by who can reach the data.

Severity follows one question: who, outside the people meant to see it, can read or change the data? The same rules drive the free RLS check and every full report.

LevelMeaning
criticalAnyone on the internet can read personal data, or read and change a whole table.
highAnyone who signs up can read personal data, anyone can change rows, or a privileged function is open to anonymous callers.
mediumA real weakness that needs a specific situation to matter, such as an UPDATE rule without WITH CHECK or a public bucket.
lowNothing exposed, but the app is likely broken, or the rule only opens non-personal data.
