PL-008critical (high without personal data)Lab

Row level security not enabled

No rules at all. With API access granted, anyone with the public key can read and change every row.

Severity
Critical (high without personal data)
Who can exploit it
Anyone on the internet
Found by
Free RLS check (static) and the full lab check
Lab proof
Automatic: anon, stranger and owner reads

ExplainWhat it is

Without RLS, a table has no row-level rules. If the API roles (anon, authenticated) have been granted access to it, anyone holding your public key can read, insert, change and delete every row through the Supabase API. The free RLS check rates it critical when the table has personal columns, high otherwise.

Supabase changed its defaults in 2026: new tables in public are no longer exposed to the API automatically (the default for new projects from 30 May, enforced on all projects from 30 Oct 2026, with existing grants kept). Older tables, and any migration that grants access explicitly, are still exposed.

Of the 70 rebuilt apps (22% of 318) where anyone with the public key could read personal data, this pattern and PL-001 were the two routes (PatchLabs lab study, n=318, Nov 2026).

ExploitExample of vulnerable code

Simplified from the patterns we see in AI-built apps. Synthetic: not taken from any real app.

supabase/migrations/…_create_leads.sql (vulnerable)
create table public.leads (
  id bigint generated always as identity primary key,
  name text,
  email text,
  phone text,
  created_at timestamptz default now()
);
-- No "alter table public.leads enable row level security;"
grant all on public.leads to anon, authenticated;

CheckCheck it yourself

check-pl-008.sql
-- 1. Tables in public with RLS switched off
select c.relname as table_name
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind = 'r' and not c.relrowsecurity;

-- 2. Can the API roles reach them?
select table_name, grantee, string_agg(privilege_type, ', ') as privileges
from information_schema.role_table_grants
where table_schema = 'public' and grantee in ('anon', 'authenticated')
group by table_name, grantee
order by table_name;

FixThe fix PatchLabs writes

PatchLabs switches RLS on and adds back exactly what the app uses. Here the public contact form keeps working and only admins can read the leads.

supabase/migrations/…_patchlabs_leak_fix.sql
alter table public.leads enable row level security;
-- The contact form can still submit
create policy "Anyone can submit a lead"
  on public.leads for insert
  to anon, authenticated
  with check (true);
-- Only admins can read them
create policy "Admins read leads"
  on public.leads for select
  to authenticated
  using (exists (
    select 1 from public.user_roles r
    where r.user_id = (select auth.uid()) and r.role = 'admin'
  ));

IntentWhen the pattern is intended

Strictly, a table with RLS off is safe if the API roles have no grants on it, for example a table only server code uses. Switch RLS on anyway: it costs nothing, and it keeps the table closed if someone adds a grant later. If you must leave it off, the report notes the reason and stops alerting once you confirm.
