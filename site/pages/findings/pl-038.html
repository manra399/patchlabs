PL-038high (critical with personal data)Code

Any signed-in user can add themselves to any team

Your data is scoped to team members, but the members table lets any user insert their own row with someone else's team id.

Severity
High (critical with personal data)
Who can exploit it
Anyone who can sign up
Found by
patchlabs-cli and the free RLS check (static, from 17 Nov 2026)
Lab proof
Not lab-proven per app: file and line in the report

ExplainWhat it is

Multi-tenant apps (teams, organisations, workspaces, clinics, stores) usually scope data with one rule: “you can see this row if you are a member of its team”. In Supabase that is a policy like team_id in (select team_id from team_members where user_id = auth.uid()). The rule is only as strong as the team_members table behind it.

PL-038 means that table has an INSERT or UPDATE policy that only checks “the row is mine”, for example with check (user_id = auth.uid()). Any signed-in user can then insert (their id, your team id), or change the team id on their own row, and every policy that asks “is the caller a member?” now says yes. Team ids are not secrets: they appear in URLs, invite links and API responses.

CauseWhy AI builders produce it

The first time a builder wires up “create a team” or “accept an invite”, the insert into team_members fails with “new row violates row-level security policy”. The quickest policy that makes the error go away is with check (user_id = auth.uid()). It reads as safe (users can only add themselves) and nothing in testing breaks, because the only person testing is already in every team.

ExploitExample of vulnerable code

Simplified from the patterns we see in AI-built apps. Synthetic: not taken from any real app.

supabase/migrations/…_teams.sql (vulnerable)
-- Data is scoped to team members...
create policy "Members read customers" on public.customers
  for select to authenticated
  using (team_id in (select team_id from public.team_members
                     where user_id = (select auth.uid())));

-- ...but anyone can make themselves a member of any team
create policy "Users can join" on public.team_members
  for insert to authenticated
  with check (user_id = (select auth.uid()));

-- or in the SQL editor: write policies on tables that other policies trust
select tablename, policyname, cmd, with_check, qual
from pg_policies
where schemaname = 'public'
  and cmd in ('INSERT', 'UPDATE', 'ALL')
  and tablename ~ '(member|membership|users_to|_users)';
-- a with_check that only compares user_id with auth.uid() is PL-038

FixThe fix

Users should never write their own membership. Remove the self-service policy and add members through a function that checks the caller is an admin of that team (or holds a valid invite).

supabase/migrations/…_fix_team_members.sql
create policy "Users can join" on public.team_members
  for insert to authenticated with check (user_id = (select auth.uid()));
create function public.is_team_admin(t uuid) returns boolean
  language sql stable security definer set search_path = '' as $$
  select exists (select 1 from public.team_members
                 where team_id = t and user_id = (select auth.uid()) and role = 'admin') $$;
create policy "Admins add members" on public.team_members
  for insert to authenticated with check (public.is_team_admin(team_id));

Creating a team needs its first admin row, so do that in one security definer function (create_team(name)) that inserts the team and the caller as admin together. Accepting an invite goes through another (accept_invite(token)) that checks the token, its email and its expiry. If the table has an UPDATE policy, drop it or add a with check that keeps team_id and role unchanged. The multi-tenant guide has the full set.

IntentWhen the pattern is intended

A few apps really are open to anyone: a public community where joining a space is the point. That is fine when every row behind the membership check is meant for anyone who signs up. Say so in a migration comment, because the same pattern on a table that guards customer data is a breach.

RateWhy it’s rated high (critical with personal data)

High: anyone who can sign up gets everything a team member sees. Critical when the tables behind the membership check hold personal columns (customer emails, patient names), because then it is PL-002 for every team at once, one insert per team.
