What we find

Eight finding types, each with a stable ID.

The first three are tested in the lab as real identities. The rest are read from your migrations by the free RLS check and listed so your engineer sees the whole picture.

Finding index
PL-001 · LAB-TESTED

Anyone with the public key can read personal data

A read rule for anon or public that isn’t scoped to the user, on a table with emails, phones or addresses.

PL-002 · LAB-TESTED

Any signed-in user can read all rows

The rule checks that someone is signed in, not that the row is theirs. Signing up unlocks everyone’s data.

PL-008 · LAB-TESTED

Row level security never enabled

With Supabase’s default grants, a table without RLS is readable through the API by default.

PL-003

RLS on, but no policies

Nobody can read or write through the API. Safe, but the app may be broken.

PL-004

UPDATE without WITH CHECK

A user may be able to change a row so it belongs to someone else.

PL-005

Policy is always true

using (true) or with check (true): the rule allows everything it covers.

PL-006

SECURITY DEFINER exposure

A function that runs with its owner’s rights, without a fixed search_path or callable by anon.

PL-007

Public storage bucket

Files served to anyone with the link. Sometimes intended; worth confirming.

Each table gets a verdict

Not every readable table is a leak.

The fix agent reads how your frontend uses each table before it decides. That’s how a business’s own public contact page avoids becoming a false alarm.

The proof

Delivery

The fix arrives as a migration you own.

A normal SQL file, timestamped to run after your existing migrations, with a comment explaining what changed and why. Plus any small code change the fix needs, listed in the report.

supabase/migrations/20261109165700_patchlabs_leak_fix.sql
-- Fix: Replace overly permissive "everyone can read" policy with owner-only access
-- The original policy "Profiles are viewable by everyone" allowed anonymous and any
-- signed-in user to read all columns (email, phone) from all profile rows.
-- Change: Only allow users to read their own profile (where user_id = auth.uid())

DROP POLICY "Profiles are viewable by everyone" ON public.profiles;
CREATE POLICY "Users can view own profile" ON public.profiles
  FOR SELECT USING (auth.uid() = user_id);

The approval model

  1. Read the proof and the risk note

    Low, medium or high, with what on the site could behave differently.

  2. Answer any business questions

    Only when the fix depends on what you intend.

  3. Approve, or mark as intended

    “Intended” tables are remembered for the app, so re-checks stop alerting on them.

  4. Apply and re-check

    Ship the migration your usual way, then re-check against your merged code.

Limits and questions

What the leak lab won’t tell you.

It proves read access on the tables your migrations build, for three identities. It doesn’t cover changes made only in the dashboard, non-Supabase backends, write rules, storage, edge functions or your app’s other code. All limits.

Is the free RLS check the same thing?

No. The free RLS check reads your migration files and flags risky rules in seconds, without sign-up. The leak lab rebuilds the database, tests real identities, writes the fix and proves it.

What counts as personal data?

Columns that look like emails, phone numbers, addresses, dates of birth and similar identifiers. A table with none of those can still have open rules; it ranks lower.

What if the data is meant to be public?

Then mark the table as intended. We remember that for the app, re-checks stop alerting on it, and the decision goes into the signed receipt.
