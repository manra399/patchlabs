Why history matters

Deleting the line doesn’t delete the key.

Git keeps every version of every file. If a key was ever committed to a public repo, anyone who clones it can find it in seconds, even after a later commit removed it.

  1. Monday: the key goes in

    An AI assistant pastes a secret key straight into a file to get the feature working.

  2. Tuesday: someone notices

    The line is deleted and moved to an environment variable. The latest code looks clean.

  3. Any day after: it’s still there

    The old commit is part of the repo. Clones, forks and copies keep it too.

what anyone can run on a public repo
git clone https://github.com/you/your-app
cd your-app
# every change ever made that mentions a live Stripe key
git log -p --all -S 'sk_live_'

Rotate first, clean up second. Rewriting history doesn’t help once a public repo has been cloned or forked. Revoking the key at the provider is the fix; removing it from history is tidying up.

What to do in the next hour.

The three keys that do the most damage when exposed. Every report links each finding to its provider’s key page.

OpenAI

  1. Create a new key

    At platform.openai.com/api-keys, ideally scoped to one project.

  2. Put it where browsers can’t see it

    In your server or edge function’s secrets, never in frontend code or a VITE_ / NEXT_PUBLIC_ variable.

  3. Deploy, then delete the old key

    Revoking it is what actually stops misuse.

  4. Check usage

    Look for spend you don’t recognise and set a monthly limit.

Why it matters: an exposed AI key lets anyone run up model bills on your account. Admin keys can also manage your organisation; treat those as critical.

Stripe

  1. Roll the secret key

    At dashboard.stripe.com/apikeys. Stripe lets you roll a key and choose when the old one expires.

  2. Update your server

    Secret and restricted keys belong only on your backend. Only the publishable key goes in the browser.

  3. Let the old key expire

    Choose the shortest expiry your deploy allows.

  4. Review recent activity

    Check your Stripe logs for requests you didn’t make.

Why it matters: a live secret key can read customers and payments and create refunds or charges on your account.

Supabase service_role

  1. Assume every table was readable

    The service_role key bypasses row level security completely.

  2. Replace the key

    In your project’s API key settings. Supabase’s newer secret keys can be revoked one at a time; the legacy service_role key changes only by rotating the project’s JWT secret, which also changes the anon key and can sign users out. Check Supabase’s docs on API keys for your project before you start.

  3. Move it server-side

    Use it only in edge functions or your backend, never in code that ships to the browser.

  4. Then fix the rules

    Run a check so the leak lab confirms what anon and signed-in users can read.

Why it matters: this key is full database access. If it’s in a public repo, the database is effectively public.

What it doesn’t do

  • Block a push before the key lands (turn on GitHub’s push protection for that)
  • Test whether a key still works
  • Scan Slack, tickets, CI logs or other non-git places
  • Private repos, until our GitHub App ships

Questions

Key scan FAQ.

Is the key scan a separate product?

No. It runs in every check, on every plan, including the free one. Keys appear in the same report as data leaks.

I deleted the key. Do I still need to rotate it?

Yes. If it was ever in a public repo, assume someone has it. Revoke it at the provider; that’s the only step that stops it working.

Should I rewrite my git history?

Optional, after you rotate. It keeps future clones clean, but copies made before the rewrite keep the key, so it’s never a substitute for revoking.

Why didn’t you flag my Supabase anon key?

It’s designed to be public, so flagging it would be noise. A committed .env file is still reported, because it often holds other secrets too; if it only holds the anon key, there is nothing to rotate.
