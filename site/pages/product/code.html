How it works

Read, match, look up, report.

Pure static reading of the files in your repo, with a time budget, so a check never hangs on a large project.

  1. Read

    The working tree and the full git history, including commits that later deleted a key.

    working tree + every commit

  2. Match

    Provider-specific key patterns and checks written for AI-built apps: edge functions, webhooks, admin pages, CORS, Firebase rules.

    supabase/functions/** firestore.rules

  3. Look up

    Dependency versions from your lockfile, checked against the OSV advisory database. Offline, this step reports “skipped” instead of failing.

    lockfile → OSV querybatch

  4. Report

    Each finding gets an ID, file, line, short redacted evidence and a one-line fix.

    PL-021 · high index.ts:4

Keys

A deleted key is still in your git history.

Git keeps every version of every file. If a key was ever committed to a public repo, anyone who clones it can find it, even after a later commit removed it. Every report links each key to the page where you revoke it.

Your Supabase anon key is public by design and isn’t flagged. What matters is the rules behind it, which PatchLabs Lab tests.

Static reading has limits. Code checks read patterns in your files; they don’t execute your app, so they can miss logic spread across services and can flag code that is safe for reasons outside the repo. Findings say what was matched so your engineer can judge. We don’t do dependency reachability analysis, DAST or pentests.

Questions

Questions about this product line.

Something not covered? Email the founder.

Do you run or build my code?

No. Code checks only read files. We never run your code, never install your packages and never call your app. The whole scan has a 120-second budget.

Where do dependency advisories come from?

From OSV, the open vulnerability database, queried with the package names and versions in your lockfile. If OSV can’t be reached, the check reports “skipped” rather than guessing.

Is my Supabase anon key a finding?

No. It ships in your app on purpose. The service_role key is different: in client code it bypasses every rule, which is PL-010.

Do Code findings get a lab-proven fix?

Lab findings get a migration proven as three identities. Code findings get a precise fix with the file and line; most are code changes your engineer makes, so they aren’t proven in the database lab. The report labels which is which.
